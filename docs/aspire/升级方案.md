# 业务系统基于 Girvs + Aspire 的升级方案

适用范围：基于 Girvs 框架、目标框架为 net10.0、需要部署到 Kubernetes 的业务系统。本文档以 NewOnlineRegistration（网报系统，20+ 微服务，生产部署在阿里云 2 套相互独立的 K8s 集群）为参照案例，但方法本身适用于任何采用相同架构模式的 Girvs 业务系统。

前置阅读：
- `docs/aspire/apphost-guide.md`——单个服务如何接入 Girvs.Aspire、AppHost 如何编排本地资源（框架层能力，已确认并实现）
- `docs/superpowers/specs/2026-07-14-aspire-k8s-production-design.md`——本方案依赖的三项框架新增能力（网关 K8s 动态发现、共享配置注入、生产资源外部引用）的设计细节

## 1. 背景与目标

现状（以 NewOnlineRegistration 为例）：

- 20+ 个业务服务用旧式 `GirvsHostBuilderManager.CreateGrivsHostBuilder<Startup>` 启动，靠 `docker-compose.yml` 硬编码 `depends_on` 编排；
- 服务发现依赖 Consul（地址硬编码在各服务 `appsettings.json`），`YarpGateway` 每 30 秒轮询 Consul Catalog 动态生成路由；
- 各服务的通用配置（日志等级、数据库连接串、JwtSecret 等）分散在各自的 `appsettings.json` 里各自维护，改配置需要逐个服务修改再重新部署，容易遗漏、不一致；
- 生产环境是阿里云 2 套相互独立的 K8s 集群，MySQL/Redis/消息队列均为阿里云托管服务；K8s 目前只承担"把容器跑起来"这一层，没有发挥其原生服务发现/配置管理能力。

目标：

1. **配置统一**：日志等级、数据库连接串、JwtSecret 等通用配置统一声明、统一注入，消除各服务各自维护的乱象；改配置以重新发布生效为已确认的可接受方式，不要求运行时热更新；
2. **依赖与服务发现全托管**：业务代码不再关心"怎么注册到 Consul""怎么拿到其他服务的地址"，全部由 Girvs 框架 + Aspire + K8s 原生能力接管；
3. **运维部署简单**：以 `aspire publish` 生成 K8s 部署清单作为唯一发布路径，替代手工维护的 `docker-compose.yml`；下线 Consul 集群运维负担。

## 2. 总体架构

`Girvs.Aspire.Hosting` 里的 `AddGirvsProject<T>`（见 `apphost-guide.md`）声明的资源依赖图，是本地开发和生产发布共享的唯一编排真相源：

- **本地开发**：`dotnet run` 直接跑 AppHost。被调试的服务作为原生进程启动（非容器化，便于断点调试）；基础设施依赖（Redis/MySQL/RabbitMQ）走本地 Docker 容器；其余未被声明为"当前调试"的服务，通过 Aspire 参数化外部资源（`AddConnectionString`/`AddParameter`）指向测试环境，与现有"改 appsettings 指向测试环境"的习惯一致，只是纳入 Aspire 统一管理。
- **生产发布**：`aspire publish`（Kubernetes publisher）把同一份声明转成 K8s 的 Deployment / Service / ConfigMap / Secret 清单，部署到阿里云的 2 套独立集群（两套集群完全独立，互不调用，各自发布互不影响）。

Consul 在新架构下完全退出（服务发现改为 K8s 原生 Service + `Girvs.Aspire.Gateway` 提供的动态路由发现，见第 4 节）；对象存储（MinIO/阿里云 OSS）不纳入 Aspire 管理范围，维持业务系统自行处理的现状。

## 3. 生产发布路径

以 `aspire publish` 替代现有 `docker-compose.yml`：

1. 每个业务服务：升级引用 `Girvs.Aspire` 包，定义根模块类并用 `[DependsOn]` 声明所用 Girvs 组件（见 `apphost-guide.md` 第 1 节）；
2. 新建（或扩展现有的）AppHost 项目，为 20+ 个服务逐一调用 `AddGirvsProject<T>`；
3. 基础设施资源（Cache/EventBus/EFCore）在 Publish 模式下自动切换为外部引用（见 `2026-07-14-aspire-k8s-production-design.md` 第 3.3 节），实际连接串通过 Aspire 参数配置源提供，来源于阿里云 RDS/云 Redis/消息队列的现网实例，不落入源码仓库；
4. `aspire publish` 生成 K8s 清单后，接入现有 CI/CD 流水线部署到两套阿里云 K8s 集群；
5. 两套集群各自独立发布，互不依赖，不需要跨集群服务发现。

## 4. 服务发现迁移：从 Consul 到 K8s 原生

业务方明确的迁移终态与框架主线一致：彻底完成服务发现迁移，不再保留 Consul 兼容路径。

- 服务间调用：迁移到 Aspire 的 `Microsoft.Extensions.ServiceDiscovery`（`Girvs.Aspire` 已提供，见 `apphost-guide.md`），发布到 K8s 后底层解析走 K8s Service DNS；
- 网关路由发现：`YarpGateway` 从"轮询 Consul Catalog"改为使用 `Girvs.Aspire.Gateway` 提供的 `KubernetesProxyConfigProvider`（watch K8s Service/EndpointSlice，事件驱动，比 30 秒轮询更实时），详见 `2026-07-14-aspire-k8s-production-design.md` 第 3.1 节；
- 迁移完成后：所有服务不再引用服务注册中心模块，不再保留旧服务发现配置节，并下线 Consul 集群（`192.168.51.183:8500`）。

## 5. YARP 网关改造

沿用现有"考生端网关 + 管理端网关"两套自建 YARP 网关分流的架构（保留是出于安全隔离考虑，不做改动），**只替换路由数据来源**：

- 每个业务服务在 `AddGirvsProject` 声明时，通过 `GirvsProjectOptions` 标注归属网关（`Gateway = "examinee"` 或 `"admin"`，可多值）和对外路径前缀（`RoutePrefix`），发布时自动写入 K8s Service 的 Annotation；
- 两套网关分别用不同 Label Selector 初始化各自的 `KubernetesProxyConfigProvider`，各自只能发现归属自己的那组服务，边界与现状一致；
- 网关的 K8s ServiceAccount 需要对应命名空间下 `services`/`endpointslices` 的 `list`/`watch` RBAC 权限，由 AppHost 在生成清单时对声明了 `Gateway` 选项的项目自动附加。

## 6. 配置统一方案

- 通用配置（日志等级、JwtSecret 等）在 AppHost 中通过 `AddGirvsSharedConfiguration` 一次性声明（见 `2026-07-14-aspire-k8s-production-design.md` 第 3.2 节），所有 `AddGirvsProject` 声明的服务自动接收，无需逐服务重复配置；
- 非敏感配置生成 K8s ConfigMap，敏感配置（JwtSecret 等）生成 K8s Secret；
- 数据库连接串、缓存连接串等基础设施类配置沿用已确认的框架能力（各组件 `ApplyAspireConnectionString`），不属于本节"通用业务配置"范畴，是两套独立机制；
- 明确不支持运行时热更新：改配置需要重新走一遍 `aspire publish` + 发布流程生效，这是已与业务方确认的可接受方式。

## 7. 本地开发工作流

沿用现有习惯——只启动当前要调试的服务，其余依赖指向测试环境：

1. 需要调试哪个服务，就在本地 `dotnet run` AppHost 时只对该服务用容器化/本地进程编排；
2. 其余业务服务的依赖，通过 Aspire 参数化外部资源（`AddConnectionString`），指向测试环境已部署的实例地址（配置来源为本地 `appsettings.Development.json` 或 user-secrets）；
3. 本地不需要安装 K8s（不需要 minikube/kind），只需要 Docker（用于被调试服务自身的基础设施依赖，如需要本地起 Redis/MySQL 容器时）；
4. Consul、MinIO 在本地开发流程中同样不再需要。

## 8. 明确不做的事

- 不要求对象存储（MinIO 本地 / 阿里云 OSS 生产）纳入 Aspire 编排，业务系统自行处理，与现状一致；
- 不追求消灭所有历史遗留场景（如极少数还在用旧启动方式的边缘服务，可后续单独评估），本方案聚焦 NewOnlineRegistration 的 20+ 核心业务服务整体切换；
- 不引入独立配置中心组件（Nacos/Apollo 等），配置更新走重新发布路径，已与业务方确认；
- 不保留 Consul 兼容开关；框架主线只维护 Aspire / K8s 服务发现路径。

## 9. 迁移步骤与检查清单

虽然是整体切换（不做灰度试点），仍需按依赖顺序推进，建议顺序：

1. **框架准备**：`Girvs.Aspire.Gateway` 新包开发完成并发布；`Girvs.Aspire.Hosting` 的共享配置注入、生产外部资源引用能力开发完成（见 `2026-07-14-aspire-k8s-production-design.md`）；
2. **AppHost 搭建**：新建 AppHost 项目，为全部 20+ 服务补齐根模块类 + `[DependsOn]` 声明，逐一接入 `AddGirvsProject`；本地验证资源接线正确（本地 Run 模式，指向测试环境的依赖能正常连通）；
3. **配置迁移**：梳理各服务现有 `appsettings.json`，识别出真正的"通用配置"字段（日志等级、JwtSecret 等），改为通过 `AddGirvsSharedConfiguration` 声明，从各服务本地配置中移除；
4. **生产资源确认**：核对阿里云 RDS 各业务库是否已建好（新架构下 Aspire 不负责建库），准备好各资源的生产连接串参数；
5. **网关改造**：`YarpGateway`（考生端 + 管理端）接入 `Girvs.Aspire.Gateway`，为每个业务服务补充 `Gateway`/`RoutePrefix` 声明；在测试 K8s 命名空间验证路由随服务上下线动态生效；
6. **测试环境全链路验证**：`aspire publish` 生成清单，部署到测试环境，验证服务间调用、网关路由、配置注入、健康检查 Dashboard 均正常；
7. **生产切换**：先切一套阿里云 K8s 集群验证，确认无误后再切第二套（两套集群相互独立，天然具备分批切换的条件，即使整体方案不做业务粒度灰度，也建议按集群分批）；
8. **下线 Consul**：两套集群均切换完成后，确认所有服务都只使用 Aspire / K8s 服务发现，再下线 Consul 集群。

## 10. 风险与测试策略

| 风险 | 缓解 |
|------|------|
| 20+ 服务一次性迁移，回归面广 | 按第 9 节顺序推进，测试环境全链路验证通过后再上生产；两套 K8s 集群分批切换，而非同时切 |
| 网关路由改造是核心风险点（自建 Provider，无成熟产品兜底） | 见 `2026-07-14-aspire-k8s-production-design.md` 第 6 节测试策略；上线前用最小拓扑（网关 + 2 个业务服务）在测试环境完整验证服务上下线时路由动态更新的正确性 |
| 通用配置迁移时遗漏字段或误判"通用/服务专属" | 迁移前逐服务过一遍现有 `appsettings.json`，形成字段清单人工评审，而非自动化批量迁移 |
| 阿里云 RDS 独立库未提前建好导致启动失败 | 迁移步骤第 4 步作为强制前置检查项，服务启动失败时的报错信息需明确指向"检查 RDS 是否已建库" |
| 网关 RBAC 权限配置遗漏 | 参照 `2026-07-14-aspire-k8s-production-design.md` 提供的 RBAC 清单示例，部署前检查 |
