# 流程防护采用“请求头前置参数 + 单流程多组合”模型

`Girvs.Gateway` 的流程防护需要在同一组业务接口（如 A/B/C/D/E）上按前置参数值动态约束不同调用顺序（如 `A→B→E`、`A→D→E`、`D→E`），且不同流程的参数名与取值均不可硬编码。我们决定在单条 `Flow` 内引入可配置的请求头前置参数（`ParameterHeaderName`）、命名接口池（`Interfaces`）及参数值到有序步骤组合的映射（`Variants`），同时保持存量纯线性 `Steps` 配置零改动兼容。

## Considered Options

- **单入口 DAG 中途按响应头分叉**：无法表达不同组合入口步骤不同（如 `ADE` 从 `A` 起、`DE` 从 `D` 起）以及同一接口在不同组合中处于不同顺位的场景。
- **支持 Query / JSON Body 读取前置参数**：会引入请求体缓冲、大小限制与反序列化开销；先限定为可配置请求头，保持 O(1) 零缓冲读取，待有明确需求时再扩展来源。
- **跨独立 Flow 共享接口**：会破坏“同一 `Method + Path` 归属唯一 `Flow`”的确定性反查，增加多流程冲突与排错成本。
- **新增下游复核响应头防跨组合伪造首步**：会对现有业务接口产生侵入改造；改为沿用 `FlowProtection` 不替代业务权限校验的定位，由下游首步接口校验业务归属，返回非 2xx 时网关自动删除首步票据。

## Consequences

- 多组合流程中同一接口可能既是某组合第 1 步又是另一组合中间步，因此网关以**请求是否携带 `X-Flow-Ticket`** 作为唯一判别信号：无票据一律按新流程首步校验（需合法前置参数且匹配组合第 1 步），有票据一律按票据已锁定的组合推进（后续不强制重传前置参数，但若携带冲突值则拒绝 `403`）。
- 未命中已配置参数值、参数缺失或同名多值头一律严格返回 `403`（不提供默认兜底组合）。
- 锁定组合后仍是严格线性序列，Redis 票据仅需增加组合标识字段即可沿用现有 `nextIndex` 状态机与 `X-Flow-Ticket` / `X-Flow-Next-Index` / `X-Flow-Completed` 响应头契约。
